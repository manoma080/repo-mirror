# Forgejo scheduler

### Forgejo Actions control repository

Install a reviewed `auto_update.py` outside the checkout and place [`forgejo-actions.yml`](forgejo-actions.yml) on the default branch of a private, trusted Forgejo workflow repository at `.forgejo/workflows/mirror.yml`. Bind its runner and `run-mirror` wrapper to that repository only. Use a different private local Forgejo repository, with Actions disabled, to store `config.json`, `failures.json` and `migrations.json`. Supply its slug and immutable ID with `--forgejo-config-repo` and `--forgejo-config-id`; this replaces, rather than combines with, `--config-repo`. Code and GitHub source credentials are independent of the Forgejo control repository. Keep the signing secret and local retry staging on protected persistent storage; back them up when relocating the runner.

Manual dispatch accepts the same six controls as the GitHub workflow. Blank source URLs run the scheduled selection; specified URLs select only those sources. `add_to_config` saves validated and pinned routes; `remove_from_config` updates only the configuration and never deletes mirrors. `destination_name` is for a single source, `visibility` applies to new destinations, and `ignore_releases` is a per-run override unless saved. Public mirrors require a public source; existing pinned names or privacy are not rewritten. Group-managed sources and pending relocations use the scheduled discovery and recovery path. Transient custom routes cannot trigger automatic relocation and use separate retry journals.

Seed the local control files from the old Forgejo authority and local state only after draining writers. Check the exact configured bytes and journal contents before cutover. The failure file aggregates per-destination worker journals, with a durable local staging marker for interrupted publication; do not start a second writer or discard local staging after a failed publication. Migration intents are written to the local Forgejo control repository before a rename and are distinct from GitHub Actions’ journals. Do not restore old local failure or migration files over newer authoritative copies.

Forgejo sorts the dispatch form alphabetically by input key. The template uses `input_01_source_urls`, `input_02_add_to_config`, `input_03_destination_name`, `input_04_visibility`, `input_05_remove_from_config` and `input_06_ignore_releases` to match the GitHub form’s order. Use these names for Forgejo API dispatches; scheduler options and GitHub inputs keep their existing names.

Explicit named destination profiles use `{"type":"forgejo","url":"http://127.0.0.1:3300","owner":"labadmin","auth":"forgejo-home"}`. The standalone updater, scheduler and sync worker each reject a mismatch with `--owner` or `--port` before starting mirroring; explicit profiles represent personal accounts and reject `--organization`. The `forgejo-home` alias means the supplied `--token-file`, not the Manobot GitHub source helper, and is not a secret or cryptographic proof of token identity. Provision the correct owner-only token file; destination API identity checks still apply. Legacy named profiles and list manifests retain their existing behavior.

The templates in this repository are not automatically installed or enabled. Check the target host's actual service and timer state before making changes.

For each Forgejo destination choose an operator policy `--asset-max-bytes N` and render `@ASSET_MAX_BYTES@` in the service or cron template. N is an integer from 1 through 2147483647 bytes. This is a transfer policy, not a detected or verified server upload limit; select a value no larger than the actual server, proxy, and operational limits. The launcher passes it to the scheduler and each worker; direct worker runs must also pass it. GitLab sources require this option before a batch starts. Links over the selected cap are preserved in release text rather than uploaded. A missing or invalid cap fails configuration.

The named Forgejo manifest supports pinned GitLab projects and a top-level `groups` list of declarations such as `{"type":"gitlab","base_url":"https://gitlab.com","owner":"team/sub","id":7,"repos":"all"}`. Only public projects directly owned by the pinned public group are discovered; shared projects and subgroups are excluded. Group onboarding requires `--config-repo` and `--asset-max-bytes`. It verifies the authoritative bytes before discovery, pins project and destination IDs, and publishes new mappings before workers start. Generated destination names have the reserved form `gitlab-` plus 24 lowercase hexadecimal digits. Only currently discovered generated mappings are scheduled, including when a group declaration is removed entirely; other explicitly configured repositories remain scheduled. Removed or transferred projects' mappings and destination repositories are retained, not deleted. Review and reconcile them manually. A partial creation or publication failure stops the batch and requires manual reconciliation; never automatically adopt an unpinned destination.

`--config-repo OWNER/NAME` names the GitHub repository holding the authoritative `config-forgejo.json`. When it is the same repository as the code remote, the manifest comes from the code snapshot; when it differs, the launcher fetches that repository's `main` separately and runs the manifest from it, so the publication target and the fetched manifest share one authority. Both use `main`, and a malformed name is rejected before any fetch. Direct scheduler invocations must supply a manifest from that same authoritative repository and branch. Authority is rechecked after discovery even when nothing needs publication; it can still change after the final check, so coordinate writers.

`config-forgejo.json` currently contains 11 GitHub mirror URLs; these GitHub repositories are the sources for Forgejo. Nine user-skipped repositories are excluded from this Forgejo batch. Review every manifest entry and its destination mapping before use. This manifest is separate from the GitHub Actions configuration. It uses one named destination and a `repositories` list: each entry has `source.url` and `mirrors.<destination>.name`; optional positive integer `source.id` and `mirrors.<destination>.id` pin identities. The empty destination settings preserve the owner and account type supplied by scheduler arguments; optionally set `account_type` to `personal` or `organization` to require a match. Multiple destinations or mirror routes are rejected. Legacy URL arrays and signed relocation entries remain supported. Named signed relocations use `mirrors.<destination>.legacy` with `url`, `name`, and `signature`, and require both IDs. Never fabricate IDs. Existing journals and signing secrets must be retained.

**Staged upgrade:** install the updated standalone `auto_update.py` outside the checkout before publishing a named manifest; old installed launchers reject the new shape. The updated launcher supports old and new manifests. Do not deploy while writers are active; coordinate upgrades and preserve credentials, journal paths and locks.

Entries may be HTTPS Forgejo repository URLs of the form `https://forge.example/owner/repo` (optional port), or any public GitHub repository URL of the form `https://github.com/owner/repo`, matching the GitHub runner's source freedom. Credentials, query strings, fragments, subpaths, and `.git` suffixes are not accepted. A GitHub source is read with the configured Manobot app credentials, so its visibility is limited by that installation, not by the URL alone; a private GitHub source therefore mirrors successfully while a private Forgejo source does not. Ordinary string entries use the final URL component as destination name. A separately verified relocation may instead use a structured mapping with an explicit destination name and original recovery identity; see [Explicit relocation bindings](../README.md#explicit-relocation-bindings). Do not publish a structured entry until the separately installed launcher has been upgraded to understand it. Source URLs are passed unchanged to workers. Case-insensitive current and historical name collisions are rejected before workers start. The standalone launcher performs structural checks, while the fetched scheduler validates the full manifest again before the batch lock and workers. Neither check proves the host actually serves Forgejo, that the source is reachable, or that a historical association is valid. Review hosts and mappings before use; do not put credentials in URLs. A mirror mapping may set `"ignore_releases": true` to skip release synchronization for that repository, leaving existing destination releases and recovery journals untouched; the worker's optional `--ignore-releases` applies only to the exact `--source` URLs of that invocation and is never written back to the manifest.

### Automatic owner-change migration

A pinned source whose repository ID still answers under a new canonical name is a verified relocation. With `--config-repo` configured, the worker mirrors into the **existing** destination using the original recovery identity and signed legacy binding, then reports the move; the scheduler finishes the transaction after the batch. It records the intent in `<journal-dir>/migrations.json` before any destination rename, rechecks both repository pins from live metadata, renames the existing destination only when its own ID already sits at the recorded name or that candidate name is free, publishes `config-forgejo.json` through a byte-conditional Contents API write with readback, and only then removes the intent. A custom `mirrors.<destination>.name` is preserved; a name that was derived from the source basename follows the new name.

Any conflict fails closed and leaves the intent pending: a later run resumes it from the recorded phase before starting a new batch and skips the already-synced repository, and a pending intent without `--config-repo` stops the batch instead of being ignored. A journal that fails authentication stops the batch before any worker starts. Publication uses the same GitHub App installation as source access (`--app-id`/`--private-key-file`); `GITHUB_TOKEN` is only a fallback for a non-refreshable single-use token, and `--config-account-type` selects the installation account type. The rename and the configuration update remain separate, non-atomic operations: an interrupted run can leave the destination renamed while the old configuration is still published until a later run resumes, and non-cooperating external writers can still race between the final check and the write.

Forgejo sources are accessed anonymously: only public repositories, refs and published releases accessible without authentication can be mirrored. Private repositories and draft releases are not visible anonymously; authenticated private Forgejo source support is not implemented. Neither the GitHub source installation token nor the destination Forgejo token is reused for Forgejo source access.

The templates use a local owner-only Forgejo token file for destination writes and a GitHub App ID and private-key file for refreshable source installation tokens. These are separate credentials from the GitHub Actions secrets; the app installation must have access to the configured source repositories. Never commit credentials or private source details.

The runner validates and snapshots the full manifest and holds an owner-only nonblocking flock for the entire batch. It starts a separate sync process per source, with up to four concurrent processes by default; set `--jobs N` (1–64) to change the limit. A top-level `host_concurrency_limits` map in the manifest can cap each source host independently — `{"default": 4, "git.example": 1}` — so a host that rate-limits bursts is mirrored in waves instead of being fetched all at once; both the `--jobs` limit and the per-host cap apply. Each worker has a 3600-second runtime limit measured from its launch; set `--repository-timeout SECONDS` to a positive finite value to adjust it. On timeout the process group receives SIGTERM, followed by SIGKILL after a two-second grace period, and the repository counts as failed; remaining repositories continue. SIGINT/SIGTERM also stop active process groups. Processes that deliberately leave their worker's process group cannot be controlled by this mechanism. Each completion is logged as a 1-based manifest position rather than a potentially sensitive repository name; completion order may differ from manifest order. Both templates select refreshable GitHub App credentials: the sync process obtains installation tokens through the app provider as needed, rather than relying on a single helper-minted token for the whole repository. A failed source does not stop subsequent sources; final exit status is 1 if any fail, 2 for configuration/lock errors, 75 if another batch holds the lock, or 130 on interruption. SIGINT/SIGTERM terminate active process groups before releasing the batch lock. The scheduler streams allowlisted progress from the shared Git and release engine as workers run: Git phase timings, release and asset ordinals, upload counts, and repository completion. Repository names, release tags, asset names, raw worker output and unrecognized errors are not forwarded. Detailed diagnostics require a separate controlled investigation. Do not run other sync processes without the same lock or other writers against these destinations.

**This is destructive reconciliation.** Shared Git logic can force-update branches and tags and delete destination-only refs. When wipe detection triggers, it first creates a private, timestamped `-wipe-` Git archive and verifies the captured refs; archive failure stops the update. This is conditional, not a backup for every destructive change. The archive contains Git refs and reachable objects only, not releases, assets, LFS objects, settings or hidden refs. The shared release policy processes source releases visible to the source credentials during initialization; on later runs it selects the first listed release, the source latest release, missing releases, visible drafts, pending releases and previously failed releases. It can update metadata and replace same-name assets for selected releases, but changes to older existing releases that are not selected can be missed. Destination-only releases and ordinary destination-only assets are retained; mirror-owned cache assets can be deleted or replaced. Forgejo cannot explicitly select the latest release: if the source latest is not already Forgejo's latest, synchronization fails rather than pretending it selected it. The destination must be private, have the expected source provenance marker, and have Actions disabled. Asset bytes are compared, but a same-size source mutation without a digest can race verification. A failure can leave earlier successful changes in place; inspect before retrying, especially after an interrupted upload.

**Empty release notes:** Forgejo's release PATCH cannot reliably clear nonempty notes with an empty body. The workaround writes exactly one ASCII space (U+0020) for a truly empty source body; it typically displays as empty, but is not byte-identical. Exactly one space is treated as logically empty in release-body comparisons and draft finalization, so an intentional one-space source cannot be distinguished from empty in those paths. Other whitespace, including two or more spaces, tabs and newlines, is preserved. Drift checks compare raw source and destination values; published finalization sends the raw source body, with Forgejo encoding empty as one space. Pending transaction markers can support recovery after interruption only when valid and the source and transaction state remain compatible; completed drafts retain their separate identity marker. Reconciliation is not atomic and can require manual review.

An isolated live Hydra test covering all 13 releases passed twice. Actual changed-asset transfers have only been exercised with mocks; they still require passing live verification. This does not replace the authorized pilot gate below.

Before an authorized bulk test, select two representative manifest sources, including one with releases and assets, and obtain authorization for their destination writes. Run each pilot separately under the same lock and without other writers. For each, verify the destination's privacy, provenance and disabled Actions; compare source and destination branch/tag refs, release metadata and asset bytes; then rerun and inspect the result for unexpected changes or conflicts. Record sanitized results without credentials or signed URLs. Reconcile any failure before proceeding. These are verification steps, not a claim that pilots have already passed.

The templates are inert files, not installed. Prefer the systemd user timer when the user manager is available; cron is a fallback. Both run at 00:00, 06:00, 12:00 and 18:00 local time (every six hours). The timer also has a startup delay, and `Persistent=true` catches up a missed calendar event when the user manager returns; cron does not. Systemd user timers require the user manager to remain running (or user lingering to be configured separately). Do not install or enable either until review and an authorized bulk test have passed. Do not use both.

After that gate, replace all placeholders in the selected template:

- `@PYTHON@`: absolute Python executable with the sync package's dependencies available; it runs both the installed launcher and fetched scheduler. Ensure `openssl` and `git` are available on the scheduler's PATH.
- `@UPDATER@`: absolute path to the separately installed, reviewed launcher, outside any checkout or snapshot.
- `@REMOTE@`: trusted repository HTTPS URL without embedded credentials (or a trusted local repository path); the launcher fetches its `refs/heads/main` on every run. SSH-style URLs are not supported.
- `@STATE_DIR@`: absolute path to an owner-only persistent directory for temporary snapshots (mode 0700). Protect its parents.
- `@JOB_LOCK_FILE@`: absolute path to the launcher job lock in an owner-controlled directory, distinct from `@LOCK_FILE@` and not a hard link to it.
- `@HELPER_PYTHON@`: absolute Python executable with PyJWT installed for the Manobot helper. This may differ from `@PYTHON@`. The launcher uses its configured default Manobot helper and installation; to override them, add `--helper /absolute/path/to/github_app.py --installation INSTALLATION_ID` before `--`. Configure the helper's credentials separately and securely for the scheduler environment.
- `@TOKEN_FILE@`: absolute path to the Forgejo token file.
- `@LOCK_FILE@`: absolute path to the persistent batch lock file in an owner-controlled directory.
- `@OWNER@`: verified Forgejo account name.
- `@APP_ID@`: GitHub App ID.
- `@PRIVATE_KEY_FILE@`: absolute path to the GitHub App private key file, not its contents.
- `@CONFIG_REPO@`: `OWNER/NAME` of the GitHub repository that holds the authoritative `config-forgejo.json`. Required for automatic owner-change migration; an unsubstituted placeholder is rejected before any worker starts, and omitting the option keeps verified moves failing closed.
- `@TIMESTAMP_SECRET_FILE@`: absolute path to a pre-provisioned, stable owner-only recovery signing secret, separate from the source manifest, Forgejo token and GitHub App key (including hard links). Generate it cryptographically with at least 32 bytes of randomness. Never put its value in a template or log. Preserve it across runs and restarts; changing it prevents verification of existing recovery markers.
- `@JOURNAL_DIR@`: absolute path to a pre-existing owner-only persistent directory for recovery journals. Preserve its contents across runs and restarts; do not place it in temporary or ephemeral storage.

### Install the launcher and understand the trust boundary

From a reviewed checkout, install a stable copy **outside** the checkout, in an owner-controlled location. For example, as the scheduler user (substitute your reviewed checkout and protected installation directory):

```sh
umask 077
install -d -m 700 /absolute/protected/forgejo-launcher
install -m 700 /absolute/reviewed/checkout/scheduler/auto_update.py /absolute/protected/forgejo-launcher/auto_update.py
install -d -m 700 /absolute/protected/forgejo-state
```

Set `@UPDATER@` and `@STATE_DIR@` to those installed paths. Updating the checkout does **not** update the installed launcher: review and explicitly reinstall it when upgrading. Protect the launcher, helper, interpreters, configuration, state, lock parent directories and credentials from untrusted writes. The fetched remote's `main` is executable code with access to the scheduler's credentials and Forgejo: trust and review who can change it, not just the manifest. A private snapshot binds the scheduler and manifest to the same freshly fetched commit. Fetch, authentication, network, snapshot or validation failure stops the job; it does not fall back to a cached checkout or run an old manifest. Network availability is therefore required for each scheduled and manual run.

An older installed launcher can reject Forgejo-source URLs, GitLab groups, or signed structured relocation entries even after the remote scheduler is updated. Stop the schedule and drain running jobs. First publish reviewed scheduler code without group declarations, then review and reinstall the matching launcher outside the checkout; verify its remote/config identity and installed command. Only then publish group declarations, pilot, and re-enable the schedule. Keep the existing recovery secret and journal. Sign each independently verified relocation with this Forgejo runner's `--timestamp-secret-file`, not the GitHub Actions secret; the complete claim format and example are in [Explicit relocation bindings](../README.md#explicit-relocation-bindings). Signatures authorize the mapping; they do not establish historical association. The fetched scheduler verifies every structured entry before starting workers: a missing, malformed or invalid signature fails the entire manifest, including ordinary URL entries. Correct and review it before retrying; do not rotate the secret to bypass the failure.

The launcher holds `@JOB_LOCK_FILE@` nonblockingly across fetch, snapshot and the entire scheduler run; contention exits 75. The scheduler separately holds `@LOCK_FILE@` for its batch; both paths must remain stable across all launchers and manual runs. Direct scheduler or sync invocations bypass the job lock and must not overlap; use the launcher instead. The updater state directory is not the persistent recovery journal: `@JOURNAL_DIR@` must be a separate directory, preserved independently.

The scheduler does not create the secret or journal directory. Provision both securely before enabling the job, owned by the scheduler user (secret mode 0600, directory mode 0700), and protect their parent directories from untrusted modifications. Back up the secret and journals securely together. Neither may be a symlink at the final path component.

The retry journal records hashed failure identifiers, not credentials or URLs, and prioritizes previously failed assets on a subsequent run; success removes their entries. Journals are separated by destination port, owner and source, and are distinct from the GitHub Actions failure file. Preserve them across deployments; they do not replace inspection of partial or ambiguous writes and are not a backup of mirrored data.

For a new installation, in a protected parent directory, generate a secret once (the exclusive create refuses to overwrite an existing one) and create the journal directory as the scheduler user:

```sh
umask 077
python3 -c 'import os,secrets; p="/absolute/protected/path/recovery-secret"; fd=os.open(p,os.O_WRONLY|os.O_CREAT|os.O_EXCL,0o600); os.write(fd,secrets.token_hex(32).encode()); os.close(fd)'
mkdir -m 700 /absolute/protected/path/journals
chmod 600 /absolute/protected/path/recovery-secret
```

The file contains 64 hexadecimal characters representing 32 random bytes; the scheduler rejects values shorter than 32 bytes after stripping surrounding whitespace. Length checks do not establish randomness. Never regenerate an existing secret as part of a deployment.

### Migrating an existing timer or cron job

Stop the old timer or disable the old cron entry; wait for running batches and direct syncs to finish. Preserve and securely back up the existing recovery secret and journal; do not rotate or delete them to clear an error. Install the reviewed launcher outside the checkout as above, provision its private state directory and distinct job lock path, and verify the trusted remote and Manobot environment. Render all placeholders using the existing scheduler lock, recovery secret and journal paths. Replace the old service or cron entry, ensuring no second schedule remains; for systemd run `systemctl --user daemon-reload`. After the review and pilot gate, enable only the selected schedule and verify the installed command and timer or crontab. Existing direct commands with the old manifest name must be retired, not merely renamed.

For a manual run, use the same rendered launcher command and both lock paths as the schedule, not `python -m repo_mirror.forgejo_schedule` directly. For example (replace every placeholder, including credentials paths):

```sh
@PYTHON@ @UPDATER@ --remote @REMOTE@ --state-dir @STATE_DIR@ --job-lock @JOB_LOCK_FILE@ --helper-python @HELPER_PYTHON@ -- --token-file @TOKEN_FILE@ --timestamp-secret-file @TIMESTAMP_SECRET_FILE@ --journal-dir @JOURNAL_DIR@ --owner @OWNER@ --app-id @APP_ID@ --private-key-file @PRIVATE_KEY_FILE@ --config-repo @CONFIG_REPO@ --lock @LOCK_FILE@
```

The launcher injects the fetched manifest; do not supply `--manifest`. Add any scheduler options after `--`.

Use single paths/names without spaces or systemd/cron metacharacters. Do not embed tokens or private keys in templates. Add `--organization` if the owner is an organization, and adjust `--port` if needed. Keep the lock path the same in every invocation and in an owner-controlled directory. Verify the Forgejo token and app private key files are owner-only and owned by the running user. Ensure the installed launcher, helper and credentials remain at their configured paths, and that local Forgejo is running. Protect the remote and its main branch from untrusted edits: each job executes code fetched from it.

For systemd, copy the rendered service and supplied timer to `~/.config/systemd/user/`, run `systemctl --user daemon-reload`, then enable/start the timer only after the gate. Verify it with `systemctl --user list-timers forgejo-mirror.timer` and inspect sanitized journal results. For cron, add only the rendered line to the existing user crontab after the gate; verify with `crontab -l`. Neither timer nor cron is configured by this repository automatically.
